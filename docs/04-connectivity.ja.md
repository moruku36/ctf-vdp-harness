# 04 接続経路設計

[English](04-connectivity.md) | [ホーム](../README.ja.md)

2026-11-09更新。予定経路であり設置記録ではありません。過去のゲスト記録はvNICなしで、ホストのシリアルコンソールとループバックVNCだけが接続経路です。

## 1. 決定済み事項と製品仕様

2026-11-02の記録を維持します。**隔離セグメント用vNICを1枚追加する（J2）**、Secure MCP Tunnelが使えれば優先する（J1）、拡張量は実測して決める（J3）。vsockは選択した実装ではありません。変更前の「NICなし」というラボ受入記録と整合させてから、新しい隔離構成を受入します。

[ChatGPTカスタムMCP公式資料](https://developers.openai.com/api/docs/guides/custom-mcp-server)で、read/writeツール、streaming HTTP／SSE、認証選択肢、Secure MCP Tunnelを確認しました。公開URLや、全サーバーでのOAuth必須は普遍的な製品要件ではありません。一方、この解析ゲートウェイは認証必須という方針を維持します。実アカウント・ワークスペースの利用可否と一連の接続受入は未確認です。

[Codex MCP公式資料](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)はstdio／Streamable HTTPを説明しています。ローカル設定がChatGPT Webのプラグイン接続に自動反映されるとは扱いません。各製品画面を同一視せず実クライアントで確認します。

## 2. 経路

| 経路 | 用途・扱い |
|---|---|
| E：Secure MCP Tunnel→ホストGW→隔離ゲストセグメント | 第一候補。実アカウント・認証・動作の受入が必要。機能や通信権限を広げない。 |
| A：認証付きHTTPSトンネル→ホストGW→隔離ゲストセグメント | Eが不可の場合の代替。従来のCloudflare Tunnel＋Access＋MCP認証を維持。認証の組合せは実MCPクライアントで検証。 |
| D：ローカルクライアント→Tailscale→ホストGW→隔離ゲスト | ホストからゲストへの経路受入後の開発・代替経路。クラウド側が暗黙にtailnet参加するとは扱わない。 |
| C：認証されたホスト管理経路経由のstdio中継 | 任意の開発経路。記録上のvNICなしゲストへ通常のSSHでは入れない。受入済み中継／コンソールか、承認済み隔離セグメントを使い、既に動くと断定しない。 |
| B：vNICなしのホスト代理／virtio-vsock | 過去の代替案。J2により不採用。 |

まず最小のオフライン解析経路を受入します。遠隔接続は別の到達点であり、ローカルのtools/list成功だけでChatGPTから解析できるとはしません。

## 3. 隔離セグメント

家庭LANから分離した専用ホストブリッジにvNICを1枚接続。ホストGWは受入済みのゲストMCPポートだけに接続します。ゲストは一般インターネットやホスト管理サービスへ到達させません。対象通信はGWまたはホストFWで中継・制御し、調査ごとの明示ポリシーを使います。

| 方向 | 方針 |
|---|---|
| GW→受入済みゲストMCPポート | 選定したサービス主体・経路だけ許可 |
| その他の着信→ゲスト | 拒否 |
| ゲスト→家庭LAN・ホスト管理面・メタデータサービス | 拒否。対象の別名を通じた迂回も不可 |
| ゲスト／中継→許可CTF／VDP対象 | 既定拒否。対象・時間・速度予算付きプロファイルだけ許可 |
| ゲスト→任意インターネット・任意DNS | 拒否 |
| 保守時の取得 | 調査と分離した管理手順。対象通信の許可へ流用しない |

FWとアプリ側検証を独立させ、解決後アドレス、転送、新規接続を検証。プロキシ・ブラウザ・アダプタの経路にも同じ制限を適用。宛先と時刻を秘匿要約し、実アドレス・認証情報はGit外へ置きます。

## 4. 外部接続の境界

クライアント接続はゲストではなくホストで終端。既存の閲覧専用MCP、管理画面、他サービスを同じエンドポイントへ含めません。トンネルを汎用ポート転送にしません。

HTTPS代替はホスト発信で確立し、ルータ・ホストへの公開着信ポートを追加しません。従来のOAuth優先方針を維持し、未認証サーバーへ切り替えません。トークンの対象・期限、利用者と調査の紐付け、認証失敗、ツール一覧、証拠取得、再接続を検証。Cloudflareのブラウザログイン成功とMCP認証を混同しません。

Secure MCP Tunnelもプロセス起動だけでは受入せず、実クライアントとの紐付けと認証主体を確認。この環境で必要なアクセス制御を満たす場合に採用します。ローカル／トンネルのどちらでも、サーバー側のスコープ制御を弱めません。

## 5. 資料・対象通信・復元

既存の読み取り専用ISO搬入（`noexec,nosuid,nodev`）を維持。将来のCTFdダウンロードは取得・一時保管までとし、資料検証とオフライン搬入を経てから解析へ渡します。取得物を直接作業領域へマウントしません。

競技モードは、許可されたCTF／VDP用の調査プロファイルへ拡張。無制限な「通信ON」ではなく、対象定義・期限・操作予算を使います。開始前にスナップショット・スコープ・機能を確認。終了後はセッション停止、一時通信解除、許可された証拠を限定取込で退避し、ゲストを復元します。通信許可だけでflagや脆弱性報告を外部提出できるとは扱いません。
