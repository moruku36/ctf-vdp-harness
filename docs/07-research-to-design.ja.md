## 研究の参考採用とOSS導入を分ける

導入判断は既存の[選定表](03-mcp-selection.ja.md)を引き継ぎます。上流の所在は再確認しましたが、特定コミットでのライセンス、コード監査、実環境の互換性、受入試験は別途必要です。

| 機能 | 候補・扱い |
|---|---|
| ソース・依存関係の観測 | 既存 `moruku36/oss-vulnerability-workbench-mcp`。管理下の試料で実解析を受入。tools/listだけでは不足。 |
| バイナリ構造・関数・逆コンパイル | [LaurieWired/GhidraMCP](https://github.com/LaurieWired/GhidraMCP)。導入済みGhidraとの互換性と限定ツールを確認。REAの保留とは分ける。 |
| バイナリ調査 | [radareorg/radare2-mcp](https://github.com/radareorg/radare2-mcp)。任意r2コマンドは公開しない。 |
| Web調査環境 | [PortSwigger/mcp-server](https://github.com/PortSwigger/mcp-server)。Burp配置・ライセンス・リクエスト制御解決後の任意候補。 |
| 対話デバッグ・接続状態 | 受入済みゲスト内ツールへの限定アダプタ。EnIGMAを参考に新規設計するもので、実装済みではない。 |
| エンコード・メタデータ・埋込データ要約 | 既存OSS優先。不足する部分だけ小さなヘルパーを作り、展開上限と実行制約を適用。 |

測定対象の課題に必要な最小構成を選びます。実装時の受入記録には、コミット、ライセンス根拠、依存関係、接続方式、ツール定義のハッシュ、権限、試料での結果を残します。古い文書のバージョンは環境記録であり、最新の対応版を保証しません。

## 今回の設計判断

次の組合せは**今回の設計としての統合案**であり、単一の論文で検証された完成品ではありません。

1. 既存AIを調査の主体とし、小さなツール一覧と追跡可能な観測を渡す。
2. 調査ごとにスコープ、復元できる仮説、証拠参照を保持する。
3. 状態が失われると困る部分に限定して継続セッションを使う。
4. AIの確信度ではなく独立した検証で結果を判定する。
5. 開発用課題の失敗から手順を改善し、評価用の答えや非公開flagを混ぜない。
6. 同予算の比較で効果を確かめてから機能を増やす。

[全体設計](08-analysis-harness.ja.md)と[評価設計](09-evaluation.ja.md)に具体化しています。
