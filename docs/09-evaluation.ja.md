# 09 評価と導入判定

[English](09-evaluation.md) | [ホーム](../README.ja.md)

実験計画であり、実測結果ではありません。MCP疎通、ツール数、AIの確信度だけで性能向上と判定しません。

## 1. 比較条件

| 条件 | 内容 | 確かめること |
|---|---|---|
| A | 現在のAI・作業手順・既存ツールを固定 | 現状の解き方と成績 |
| B | 同じAI＋選定した限定OSSツールをMCP経由で利用 | 機能追加そのものの効果 |
| C | B＋調査状態、必要な継続セッション、証拠ページ、仮説台帳 | 接続だけではないハーネスの効果 |
| D | C＋失敗分析から改訂して固定した作業ガイド | 手順改訂の追加効果 |

AとBのツール差は意図した実験要因として記録。B→Cで状態・インターフェース、C→Dで手順改訂を分けます。上流ツールやモデルが変わった場合は、実験をやり直すか別実験として扱います。

実モデル・推論設定、クライアントモード、入力、時間・ツール呼出・観測可能なトークン予算、開始状態、許可通信を揃えます。取得できない指標は未取得とし、サブスクリプションUIからAPI費用を推定しません。人のヒントは記録して別集計。会話・調査ID・作業領域を新規にし、VMを復元して条件間の証拠流用を防ぎます。

## 2. 課題集合

まず所有する合成試料5件で統合確認します。正常入力、不正入力、長い出力、時間超過・取消、復旧を含め、性能結果としては扱いません。続いて、利用権を確認したローカル課題10件を開発用、別の20件を試行評価用とする案です。実施前に実課題一覧、分野配分、版・ハッシュ、採否条件を固定。小標本なので探索的評価とします。

可能な範囲でリバース、フォレンジック／変換、ソース解析、ローカルWebを含めます。現行VMで扱えない分野を無理に載せず、未対応課題を正答扱いしません。公開課題は学習済みの可能性を限界として記載し、可能なら新規作成した変種や非公開の管理下課題を使います。両条件とも解答を探す無制限Web検索は行いません。

VDP型評価は、既知の脆弱版と対応する非脆弱版・修正版を使う**別集合**とし、レビューで正解を定義。CTFの分母に混ぜません。将来の実VDP作業は許可範囲で別集計し、ベンダー応答時間・受理は外部結果として扱います。

## 3. 指標

| 指標 | 定義 |
|---|---|
| CTF検証済み正答率 | 予算内にローカル検証で正答した課題／事前に定めた対象課題。自己申告不可。 |
| 初回試行 | 課題・条件ごとに独立した1試行。複数回中の成功率と分け、best-of-kをpass@1と呼ばない。 |
| 時間・資源 | 正答までの時間、全所要時間、呼出数、CPU・最大RSS・ディスク、取得可能なトークン／API費用。失敗も予算消費に含める。 |
| 証拠の質 | 参照原文が存在し、版・前提が揃い、初見の確認者が再現できる。 |
| VDP型precision | 独立確認できた発見／報告した全発見。重複統合と正解条件を事前定義。 |
| VDP型recall | 管理下の既知事例で発見できた件数／対象既知件数。実環境の未知の陰性例から算出しない。 |
| 運用信頼性 | 実行失敗・時間超過、状態消失、証拠欠損、重複操作、終了・復元成功。 |
| ポリシー違反 | 対象外実行、未許可通信、調査間の不正参照、機微情報書き出し。重大度と再現情報は非公開保管。 |

根拠不足・判断不能・見逃しを落とさず報告。時間超過・基盤失敗は主集計の課題数に残し、必要なら基盤正常時の補助集計を併記。繰返し評価は回数、制御できる乱数種、結果分布を明示します。

同じ課題で改善・悪化・不変を比較し、標本数が許せば不確実性区間を示します。20件で全CTF・VDPへの一般化はしません。分野別成績を残し、ある分野の改善で別分野の悪化を隠しません。

## 4. 制御機能の受入

性能を測る前に、以下を実装時に検証します。

- スコープ期限・変更、無効ツール、不正スキーマ、パストラバーサル・シンボリックリンク、巨大／圧縮入力、他調査の証拠ID。
- ローカル試験ネットワークでDNS・転送・別アドレスの制限。自宅LANを試験対象にしない。
- 時間超過、取消、切断、再起動、残存プロセス、資源不足、復元。
- 命令文に似た対象出力でも権限変更・外部書き出しを起こさないこと。
- 合成の機微マーカーが監査・秘匿処理済み成果へ出ず、原文取得に認可が必要なこと。

実認証情報は使いません。これらは今後の実装受入であり、今回の文書更新で実行済みの試験ではありません。

## 5. 失敗からの改訂

失敗を、搬入／スコープ、機能不足、接続仕様の曖昧さ、状態消失、証拠不足、早すぎる断定、検証器、資源、モデルの推論限界に分類。可能なら一度に一要素を変更します。

失敗に根拠がある短い作業手順とアダプタ挙動だけを改訂し、評価前に版を固定。評価課題の答え・flag・生の非公開記録をスキルやメモリに入れません。調整に利用した評価課題は開発用に移し、次の主張には新しい未使用集合を使います。

## 6. 導入判定

試行段階の合格条件案です。

1. **統合**：定義した契約・制御試料がすべて合格。重大な対象逸脱・漏えい不具合がない。
2. **オフライン試行**：マニフェストと証拠から再現でき、終了処理に成功。A／B／Cの結果と悪化例を記録。
3. **有効な補強**：固定予算内で独立確認した正答・再現が改善し、説明できない悪化がない。不明・横ばいなら単純な受入済み構成を維持し、改善未証明と報告。
4. **通信／VDP**：スコープ、速度、認証、リクエスト制御の別受入をローカル対象で通してから、許可された実対象へ進む。
5. **広い性能主張**：より大きな未使用集合と、条件を揃えた反復が必要。改善率を事前に約束しない。

小規模試行は開発継続の根拠にはなりますが、報奨金対象、誤検知ゼロ、一般的なモデル優位性を保証しません。[レポート雛形](../templates/run-report.ja.md)に最低限の証拠を残します。
